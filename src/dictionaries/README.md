# 内置词典

命中词条时**完全跳过 DeepSeek API** 直接返回结果：零延迟、零费用、离线可用。
未命中则自动回落到原有的「缓存 → API」流程，用户无感知。

**词典仅在中→英方向生效**（词表是中文 → 英文命名的映射）。

> 更新：英→中方向现也已接入**反查**（`lookupDictionaryReverse`）——把英文命名切词后
> 逐段比对词表，全部段有唯一释义则拼合返回；组成段无独立词条时按整名兜底
> （`cachePenetration` → 缓存穿透，`getUserName` → 用户名）。
> 歧义段（如 get/is 这类高频词根）不参与反查，宁缺勿错，未命中交由 API 兜底。

## 设计原则：零外部依赖

`lookupDictionary(text)` 是**纯函数**——同样的输入永远返回同样的结果。

它不接受生态、语言、场景等任何外部选项，这是刻意的：

| 曾经的做法                     | 产生的问题                                                                 |
| ------------------------------ | -------------------------------------------------------------------------- |
| 按语言分 `general` / `csharp`  | 「事件/属性/字段/实例/泛型/事务」在 Java/TS/Python 写法相同，却被塞进 C# 层 |
| 用生态选项决定是否命中         | 输入「委托」在通用生态 MISS、切到 C# 才 HIT；用户看到「切个按钮词典就变了」 |
| 用生态选项微调命名约定         | 为 5 条词的 `I` 前缀 / `Async` 后缀，在界面常驻一排 7 个选项，不成比例      |

**结论：词典只给出基础拼写**（「接口」→ `Service`）。
需要 `I` 前缀、`Async` 后缀这类语言惯例时，由用户自行调整——插件不猜。

## 文件组织

| 文件             | 说明                                             |
| ---------------- | ------------------------------------------------ |
| `index.js`       | 查询入口（异步懒加载），**唯一对外 API**          |
| `words.json`     | 全部词条，扁平结构，无语言维度                   |
| `categories.json` | 分类索引（词表页按类别浏览用），`{类别id: {label, words[]}}` |

## 词条结构

顶层 key 是**中文原文**（与输入 trim 后精确匹配），值为四个命名类型：

```json
{
  "用户名称": {
    "variable": [
      { "camelCase": "userName", "snake_case": "user_name", "PascalCase": "UserName" },
      { "camelCase": "username", "snake_case": "username", "PascalCase": "Username" }
    ],
    "method": [
      { "camelCase": "getUserName", "snake_case": "get_user_name", "PascalCase": "GetUserName" }
    ],
    "constant": [
      { "camelCase": "USER_NAME", "snake_case": "USER_NAME", "PascalCase": "USER_NAME" }
    ],
    "class": [
      { "camelCase": "UserName", "snake_case": "user_name", "PascalCase": "UserName" }
    ]
  }
}
```

### 硬性约束

`lookupDictionary()` 会校验每个词条，**不合法则跳过并打印警告**（不会让翻译崩溃）：

- 四个字段 `variable` / `method` / `constant` / `class` **全部存在**且均为**非空数组**
- 每个候选必须同时具备 `camelCase`、`snake_case`、`PascalCase` 三个**非空字符串**

### 哪些风格会被真正显示

UI 只渲染各类型有意义的风格，其余字段仍须填写（结构完整性），但**填什么都会被忽略**，建议按惯例填成与主风格一致：

| 类型       | 实际显示的风格                          | 惯例填法                    |
| ---------- | --------------------------------------- | --------------------------- |
| `variable` | camelCase / snake_case / PascalCase（另派生 kebab） | 三种风格各不相同 |
| `method`   | camelCase / snake_case / PascalCase     | 三种风格各不相同            |
| `constant` | **仅** snake_case（以 UPPER 展示）       | 三个字段统一填全大写下划线  |
| `class`    | **仅** PascalCase                        | 三个字段统一填 PascalCase   |

> ⚠️ 注意 `constant` 与 `class` 的惯例填法看起来"不合规"（如 `constant.camelCase` 是全大写的 `USER_NAME`），
> 这是**符合现有约定的**——它们只用于占位，实际渲染取上表指定的单一风格。

## 词条选取建议

- **候选数量**：`variable` / `method` 建议 1-2 个（常用优先），`constant` / `class` 1 个即可
- **命名质量**：优先业界惯用名（如「编号」用 `id`），缩写遵循通行写法
- **保持中立**：存基础拼写，**不要**预先加 `I` / `Async` 等语言专属缀
- **不要收录**生僻词或需要语境才能判断的词——这类交给 LLM 更合适

## 新增词条检查清单

改完词表后**务必运行测试**：

```bash
npm test
```

测试脚本 [scripts/test-dictionary.mjs](../../scripts/test-dictionary.mjs) 会校验结构、重复与命名规范，
发现问题时以非 0 退出码结束，可直接接入 CI 或 pre-commit。

- [ ] 中文 key 与用户实际输入一致（「手机」vs「手机号」这类近义词可各收一条）
- [ ] 四个字段齐全且非空
- [ ] 每个候选三种风格拼写正确
- [ ] `snake_case` 全小写下划线，`camelCase` 首字母小写，`PascalCase` 首字母大写
- [ ] **未预先添加**语言专属前缀/后缀（`I` / `Async`）
- [ ] 已运行 `npm test` 且全部通过

## 测试覆盖

`npm test` 包含 57 项检查，分六类：

| 分组             | 检查内容                                                                 |
| ---------------- | ------------------------------------------------------------------------ |
| **结构完整性**   | 四类字段齐全、均为非空数组、三个风格字段非空；无残留 `conventions`        |
| **重复检测**     | 重复顶层 key（会被静默覆盖）、词条内重复候选、同类型渲染值重复、跨词条同义、跨词条首选变量名撞车（仅告警） |
| **命名规范**     | 被渲染风格的拼写合法性、无预置语言缀、key 无空白                          |
| **查询行为**     | 全部词条可命中、返回结构同构、纯函数确定性、各类边界输入                   |
| **来源提示一致性** | 状态栏提示与实际执行路径是否一致（防止"提示说谎"，见下）                 |
| **分类数据**     | `categories.json` 结构、覆盖一致性（双向：分类引用的词必须在词表、词表词条必须已分类）、`listDictionary` 查询行为 |

### 为什么校验"来源提示一致性"

界面会在状态栏提前告诉用户「走内置词典」还是「调用 API」。这个提示一旦与实际路径不符，
就是在骗用户（例如提示"不消耗 API"却真的发了请求）。因此测试做源码级校验：

- `pendingSource` 与 `translate()` 必须用**同一个判定表达式**
- 词典查询必须**早于 API Key 校验**（否则未配 Key 时提示与行为矛盾）
- 全部词条都会被提示为「内置词典」；未收录词必然提示走 API
- 英→中方向不启用词典，提示固定为 API

### 关于"重复"的判定口径

测试区分**两类重复**，处理方式不同：

- **算失败**（会真的造成问题）：
  - 顶层重复 key —— `JSON.parse` 用后者覆盖前者，词条**静默丢失**，最隐蔽
  - 词条内完全相同的候选 —— UI 会出现两行一模一样的命名
  - 同一类型下渲染值重复（如两个候选的 `camelCase` 相同）
- **仅告警**（属正常）：
  - 不同中文 key 产出相同英文 —— 如同义词「账户 / 账号」都叫 `account`，
    这是期望行为，测试会列出来供人工确认，但不判失败

> 当前有 4 组同义词：`用户名==用户名称`、`账户==账号`、`接口==服务`、`新增==创建`。
## 设计说明

**为什么词典结果不写入缓存？**
词典是本地常量，"缓存"它只会占用 uTools db 空间、7 天后过期，还会稀释历史面板的
「缓存命中率」统计（该指标用于反映真实节省的 API 调用）。

**为什么词典先于 API Key 校验？**
词典是纯本地数据，未配置 Key 的用户也应能享受词典直译。

**体积与懒加载**
词表通过动态 `import('./words.json')` **懒加载**：独立成 `assets/dict-*.js` chunk，
仅首次查词时才加载，之后整个会话复用缓存。**加词只会增大词典 chunk，不影响启动体积**
（当前主包 ~133 KB 恒定，词典 ~462 KB / 1263 条）。

> ⚠️ 该机制依赖**多文件产物**。`vite-plugin-singlefile` 会把动态 `import()` 一并内联，
> 导致懒加载完全失效（实测产物仍是单个大 HTML），因此 `vite.config.js` 中已移除该插件。

因此 `lookupDictionary()` 与 `dictionarySize()` 都是**异步**的，调用方必须 `await`。
若词条继续增长到数千条，可进一步按类别拆成多个 chunk（如 `words-db.json`、`words-ui.json`）。
